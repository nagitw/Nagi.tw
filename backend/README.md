# Nagi AI — isolated Raspberry Pi / Debian 13 deployment

Status: local implementation, **not deployed**. No SSH assumed. Do not modify, restart or reuse existing medical research services, Ollama units, tunnel credentials or ports without a separate conflict review.

## Boundaries

GitHub Pages serves static files only. Browser POSTs NDJSON to `https://api.nagi.tw/chat`. Dedicated outbound Tunnel → `127.0.0.1:8765` FastAPI → `127.0.0.1:11434` Ollama. No public listeners for FastAPI/Ollama/SSH, no router port forwarding. Do not add SSH ingress. CORS is only a browser restriction, **not authentication or abuse prevention**. No frontend secret exists. API is intentionally anonymous, globally limited to 10 validated requests/minute (all clients share quota), one active inference, no waiting queue, maximum 25s. Single Uvicorn worker required. Multiple replicas require a shared limiter before deployment.

Input: JSON only, 8192 byte body including chunked uploads, 5s upload timeout, 1000 character question, en/zh, unknown fields rejected. Output: 512 model tokens, 8000 characters, 128k upstream bytes, 16k line buffer. No arbitrary model/options/tools/system prompt, shell, URL retrieval or chat persistence. System prompts cannot guarantee factuality; model output remains untrusted text. Client never renders model HTML. Default browser timeout 30s, cancellation closes upstream. Automatic retry only once on pre-stream 502/503/504; manual retry retains the question. Partial responses are never automatically replayed.

## Prepare a dedicated release (operator, not executed)

1. Inventory CPU/RAM/disk, `ss -lntp`, existing service names, user accounts and firewall; choose an unused dedicated port. If 8765 or 11434 conflicts, stop and review isolation; do not change an existing service. Hardware capacity and coexistence with medical workloads remain UNVERIFIED. Use a separate host if resource isolation cannot be guaranteed.
2. Create service users `nagi-ai` and `cloudflared-nagi` with no login; root-owned `/opt/nagi-ai/releases/<release-id>`, `/opt/nagi-ai/venv`, `/etc/nagi-ai`, `/etc/cloudflared-nagi`, `/var/lib/nagi-ai`. Use a dedicated venv, never system pip. Install `requirements.lock` into that venv; run `pip check`, `pip-audit -r requirements.lock`, pytest, and retain the lock and wheel artifacts with the release. The lock contains exact locally resolved production/transitive versions; ARM64/Python 3.13 compatibility and wheel hashes must be independently verified before deployment. `requirements.txt` is only for intentional dependency upgrades followed by lock regeneration/audit.
3. Build the website. Manually review `dist/knowledge.json` (published titles/descriptions/routes only); copy that **approved local file** to `/var/lib/nagi-ai/knowledge.json`, root-owned, service-readable, non-writable by service. Record `sha256sum`; set the exact digest in `/etc/nagi-ai/api.env` from `deploy/api.env.example` (root-owned, mode 0640). Startup rejects missing/mismatched digest. Never copy raw source, drafts, internal records or private medical data. Backend performs no network knowledge fetch and reads no other knowledge files.
4. Provision a **dedicated** Ollama instance/account and model only after port/resource conflict review. Bind `OLLAMA_HOST=127.0.0.1:11434`, `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_MAX_QUEUE=1`; disable any Ollama cloud use, preload the approved local model. Firewall outbound access as appropriate after model download. Never repoint/restart an existing research instance. Ollama installation, local-only binding, model provenance and ARM performance remain UNVERIFIED.
5. Point root-managed `/opt/nagi-ai/current` symlink to the reviewed release. Install the dedicated `deploy/nagi-ai.service`. Verify unit with `systemd-analyze verify`, then operator-authorized `daemon-reload` / enable/start. API unit is unprivileged and read-only; model memory is separate and needs its own resource budget. Do not enable on a shared medical Pi without an approved budget.
6. Create a dedicated named Cloudflare Tunnel, DNS `api.nagi.tw` to its assigned target, separate credentials and user. Adapt `deploy/cloudflared.yml.example` and service file; credentials/config only readable by tunnel user. Run `cloudflared tunnel ingress validate` and `cloudflared tunnel ingress rule https://api.nagi.tw/chat`. Catch-all is 404; only chat/health routes go to API. Do not print credentials, tokens or tunnel secrets into logs/repo. Outbound tunnel requires no inbound ports. Add edge rate limiting/bot controls consistent with the Cloudflare plan; global local limiter is defense in depth, not DDoS protection.

## Health, logging and verification

`GET /healthz`: process alive. `GET /readyz`: local Ollama responds and configured model installed (does not prove an inference fits Pi resources). `POST /chat` JSON `{ "question": "Who is Nagi?", "locale": "en" }` returns newline-delimited delta/done; failures before headers 503, after stream starts error event with no done. Client treats incomplete/invalid/error stream as unavailable. Test zh and en, cancellation, timeout, busy and 429, oversized/chunked requests, invalid origin and invalid fields. Run `python -m pytest` from backend directory.

Structured request log contains random request ID, HTTP header status and total request duration only. It deliberately omits question, answer, URL/query, headers, client identity and exception detail. A 200 stream status does not prove that a done event was delivered. Response ownership covers startup/downstream send failures and stalled sends; upstream closure is shielded with a 2s cleanup bound before releasing the reservation. If closure cannot be confirmed, subsequent inference/readiness fail closed until service restart. Uvicorn access logging disabled; keep reverse proxy/Cloudflare body capture and debug logging disabled. Apply short journal retention; review Cloudflare logging settings separately. Monitor 429/503 and system resource pressure without recording conversations.

Verify `ss -lntp`: API and Ollama **loopback only**, no public SSH; confirm host/router/cloud ingress denies public 22/8765/11434. From an authorized external host, verify HTTPS certificate, HTTP→HTTPS, approved CORS and disallowed origin, nosniff/no-store, streaming without buffering, closed internal ports. Require real inference smoke tests on Pi and through Tunnel. None of these are proven by local fixture tests. Add HSTS only after HTTPS for required hosts works. No private API keys in Astro PUBLIC variables.

## Rollback

Before deployment retain previous root-owned release directory, pinned venv/wheel set, approved knowledge+digest, environment snapshot (secure local storage), unit/tunnel config and model version. Record last good IDs. Stop only `nagi-ai`, atomically repoint current to the last good release, restore its dedicated venv and matching approved knowledge/digest, restart only `nagi-ai`, then health/readiness/stream smoke tests through the existing tunnel. Restore dedicated tunnel config only if changed and verified. Never roll back research services, flush the shared firewall or alter unrelated DNS. If smoke tests fail, stop the dedicated tunnel/API and keep frontend offline. Never delete historical release artifacts to perform rollback.

## Frontend enablement

After operator confirms domain ownership/DNS, backend isolation, TLS and tests: build with `PUBLIC_PENGUIN_AI_MODE=api` and `PUBLIC_PENGUIN_API_URL=https://api.nagi.tw/chat`. Until then leave offline. Pages settings/custom domain must be separately verified; CNAME file alone does not activate DNS or TLS. No push/merge/deploy is authorized by these instructions.
